# ZT9101DV20 experimental Linux support

This branch adds a DV20 boot path recovered from the supplied Windows driver
`usbwifi_ndis6.sys` (INF version 16.59.44.912, SHA-256
`75b932f955dee135792be606d7fc4cbc0d53d61cd6ebe265fdf299cc1768fad3`).
It has been statically compared and tested without the physical adapter.
Hardware initialization, association and traffic still need device testing.

## Device selection

| USB identity | Handling |
|---|---|
| `2310:1a2b` storage/CD mode | Standard media eject via usb_modeswitch, then re-enumerate |
| `2310:9086`, interface `ff/ff/ff` | New `ZT9101DV20_Info` profile |
| `350b:9101` | Existing XV20 profile retained |
| `350b:9086`, `350b:9106` | Existing XV30 profile retained |

The DV20 USB profile is selected when `CONFIG_ZT9101DV20_SUPPORT=y` (default).
Set it to `n` at make time to restore the old XV20 handling for `2310:9086`.
There is no matching of the storage interface to the WLAN USB driver: a CD-ROM
interface uses a different protocol and must be switched first.

## Differences recovered from the Windows implementation

| Windows address | Recovered behavior | Linux implementation |
|---|---|---|
| `0x140021CFC` | `AC |= 02`, `F8 |= D0`, `98 = FF`, `200 = 00100000`, then `80100000` | `zt_dv20_usb_prepare()` |
| `0x140021D80` | MCU disable/enable; clear `03.bit2`; select ROM using `F4.bit0`; set `03.bit2`; delay 10 ms | `zt_dv20_rom_prepare()` and DV20 firmware download |
| `0x1400230F4` | Two-segment 0xAFFA/0x9188 container; skip DSP's first 32 bytes | Validated `zt_dv20_parse_image()` |
| `0x1400219E0` | Firmware payload in 488-byte blocks, XOR checksum, zero padding | Existing bulk transport with safe padding/checksum |
| `0x140021D80` | Poll `0x3E8 == 0x55`, no mailbox request writes | `zt_dv20_wait_ready()` |
| `0x14000B1F8` | READ_VERSION opcode 1 with no input DWORD | Conditional argument length in `zt_mcu_get_chip_version()` |
| `0x140009E94` | Invalidate HW, initialize/enable ARS, then FW_INIT; no newer RF power table | Conditional initialization order in `hw_info.c` |

The nine-DWORD FW_INIT layout and the common command numbers match the Linux
implementation. RX aggregation is enabled only when supported by the Linux
build, rather than enabling it merely because Windows does so. The other
chip profiles continue to use their existing firmware and boot sequence.

The original DV20 M0 is exactly 78 * 488 bytes. The bulk protocol requires a
final padded block, so this case must not read four bytes past a firmware
allocation. Chunk padding and checksum now explicitly use zeros.

The DV20 path also avoids the legacy full power-off before power-on and the
USB reset during module disconnect. The former differs from the recovered
normal Windows sequence, and both can discard the active USB personality.
Whether these were responsible for the reported storage fallback still
requires a device trace. Firmware/probe failure now releases the interface,
USB reference and HIF record instead of leaving stale driver state behind.

## Build and install on the target machine

Install matching kernel headers/build tools and usb-modeswitch first. Build in
this source directory:

```sh
make -j4
modinfo -F version ./zt9101_ztopmac_usb.ko
sudo make install-dv20
```

The expected module version is `1.2.1800-dv20.1`. `install-dv20` installs the
module, device firmware, an absolute configuration path, and the CD switching
rule. `make install` alone retains its old behavior and installs only the ko.
Existing different firmware/configuration files are not silently replaced.
For an installation-layout preview without root:

```sh
DESTDIR=/absolute/path/to/project/tmp/dv20-preview make install-dv20-config
```

Before switching, make sure the new module is the one loaded. If an old module
is loaded, removing it disconnects other adapters using that same driver.
For a direct test using the exact newly compiled module:

```sh
sudo modprobe cfg80211
# Run only if replacing an already loaded old module:
sudo modprobe -r zt9101_ztopmac_usb
sudo insmod ./zt9101_ztopmac_usb.ko cfg=/etc/zt9101/wifi.cfg
cat /sys/module/zt9101_ztopmac_usb/version
sudo usb_modeswitch -c config/usb_modeswitch/2310:1a2b
lsusb
ip -br link
dmesg | tail -n 150
```

Successful boot should report `ZT9101DV20 firmware running`, and the device
should enumerate as `2310:9086`. A different ID or return to storage mode is
evidence to investigate, not proof of successful support. The module's
`dv20_fw` parameter accepts a firmware name relative to `/lib/firmware`; there
is no silent fallback to the newer XV20 firmware when DV20 firmware is absent.

## Regression tests

`script/test_dv20.c` executes the same parser and register-sequence helpers as
the kernel driver, with transport callbacks that record operations. It covers
ROM selection, I/O errors, mailbox readiness/timeout, real firmware offsets,
truncation, overlapping segments, length underflow and zero-padding. Compile
the test binary under the project's tmp directory and pass
`fw/zt9101dv20.bin` as its argument. This does not replace hardware testing.
